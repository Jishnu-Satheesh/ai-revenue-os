# Campaign experience — proposed data and workflow contracts

- Status: design proposal, not an inventory of existing exports or database fields. Names marked **new** below are proposed implementation targets. Confirm product decisions in the [design](../specs/2026-09-12-campaign-experience-design.md) before adopting them.
- Preserve the existing campaign, approval, asset, measurement and memory records. Read the [audit](../../verification/campaigns/2026-09-12-workflow-audit.md) for actual implementation evidence. Do not retrofit past approvals to new meaning.

## C01 — Separate readiness for research, preparation and launch

- New domain file: `src/domain/campaigns/readiness.ts`; new public domain type `CampaignReadiness` with independent `proposal`, `creativePreparation`, `launch` and `measurement` results.
- Each result contains `status: ready | needs_input | blocked | unknown`, a list of typed blockers, checked time and source revision bindings. A blocker contains a stable code, affected phase/action, safe explanation and typed repair target; the client turns a repair target into a permitted route.
- Confirmed D07: a missing numeric profit estimate or unavailable external market research is a visible evidence gap, not by itself a reason to hide a supported internal proposal. Keep proposal presentation, approval for preparation and launch readiness separate. Unsupported factual claims, invalid source ownership and absent spending authority do not become eligible through this rule; implement it in Campaign proposal admission, not generic Decision execution qualification.
- Existing `verifiedChannelLimits` remains execution evidence until explicitly refactored. Introduce a separate bounded draft-content contract rather than telling an internal draft that unverifiable platform limits are verified. A launch action requires current provider-specific validation of its exact output.
- Required distinctions: source facts unavailable; no declared subject; synthetic path not permitted; proposal not approved; required creative rejected; render verification pending; content changed; contract expired; provider mapping missing/ambiguous; scope revoked; adapter absent; measurement unavailable; budget missing; publish confirmation pending.
- Backend callers consume typed outcomes, not raw Error strings. UI can prepare supported internal work and show exact future launch blockers. No model invents limits or changes readiness authority.

## C02 — Campaign proposal and the first approval

- New domain file: `src/domain/campaigns/proposal.ts`; public proposed schemas/types `campaignProposalDocumentSchema`, `CampaignProposalDocument`, `CampaignProposalVersion`, `CampaignProposalDecision`.
- Document `schemaVersion: 1` includes: title; business problem; objective; audience; nullable offer reference and explicit no-offer choice; requested channels with organic/paid distinction; creative deliverables by format/language/count; timing; proposed media budget; generation cost ceiling; success plan; pause policy reference; evidence references; memory context manifest reference; assumptions; limitations; readiness results.
- Budget is integer minor units plus ISO currency; the immutable document stores the proposed amount. The read model derives proposed/approved labels from appended decisions, never from a mutable document flag. Do not represent unknown as 0. Organic-only media budget can be absent, separately from generation cost.
- Success plan includes primary metric key, baseline source/revisions/window, observation window, reporting/settlement delay, candidate registered measurement method/template, target where supported and missing-data list. A plan can be presented before every launch prerequisite is satisfied, but must say so. Any eventual realized-outcome claim uses the existing evidence engine's validated method.
- Evidence reference is a discriminated union over existing source-owned records, carrying organization binding, source revision, observation window and support type. Business Memory context refs are distinct from market claim citations. Do not accept arbitrary URLs as evidence IDs for internal facts.
- New tables: `campaign_proposals` for identity/current state; `campaign_proposal_versions` for immutable strict documents/digests; `campaign_proposal_decisions` for append-only actor decisions.
- Proposal identity fields: UUID id, organization_id, source_kind (`manual_request`, `business_signal`, `next_test`), source linkage validated by a controlled source reader, deduplication fingerprint, current_version_id, optional linked_campaign_id, created_at and updated_at. New source kinds are proposal kinds, not existing Campaign enum values. Proposed identity states: `researching`, `needs_input`, `ready_for_review`, `changes_requested`, `approved_for_preparation`, `snoozed`, `dismissed`, `superseded`, `cancelled`; run failure is separately persisted and surfaced as attention.
- Version fields: organization_id, proposal_id, id, increasing version, document, digest, bound source revision manifest, created_at, creator identity. Unique `(organization_id, proposal_id, version)`; composite tenant foreign keys. Document and digest are immutable.
- Decision fields: organization_id, id, proposal_id, proposal_version_id, proposal_digest, actor_id from auth context, decision (`approved_for_preparation`, `changes_requested`, `snoozed`, `dismissed`), nullable reason/instructions, optional snoozed_until and timestamp. Reason/instructions are untrusted human input; approval has no money-moving authority.
- Approval transaction rechecks role, exact current version/digest, source freshness, proposal eligibility and preparatory cost limits; appends decision; establishes one campaign link; saves generation intent atomically. A duplicate request replays the committed result. Different content under the same key is refused.
- When originating without a legacy Decision opportunity, explicitly add `campaign_proposal` to Campaign source kinds with `proposal_id` and a check requiring exactly the appropriate source link. Do not manufacture a qualified Decision opportunity or misuse `manual_brief` to avoid a schema amendment. Existing manual/decision campaigns remain readable.
- Bundle provenance links to exact proposal version/digest. The approved proposal owns intent until bundle preparation; the immutable bundle/launch set owns exact authorized execution. They cannot independently change offer/audience/budget.
- Proposed API under organization Campaign module: `GET/POST /campaign-proposals`, `GET /campaign-proposals/:proposalId`, `POST /campaign-proposals/:proposalId/decisions`, `POST /campaign-proposals/:proposalId/revisions`.
- Read/list payloads are typed DTOs; decision body names exact version/digest, decision, optional reason/date and idempotency key. Never accept actor or organization authority from request JSON.
- Proposed service exports in new `application/proposal-service.ts`: `createCampaignProposalService`, with `request`, `decide`, `requestRevision` and `read`; implementation owns strict input/outcome types. Proposed SQL RPC names: `request_campaign_proposal`, `decide_campaign_proposal`, `complete_campaign_proposal_version`. Verify names do not collide at implementation time.
- Domain outcomes: saved/replayed, needs_input, stale_version, expired_evidence, forbidden, conflict, unavailable. Exact HTTP mapping: 401 unauthenticated; 403 unauthorized; 404 not found/not visible; 409 version/idempotency conflict; 422 invalid business prerequisite; 503 unavailable dependency. Accepted background intent may return 202 with saved domain state; it is never proof of generation completion.

## C03 — Research and preparation lifecycle

- New `campaign_research_runs` contains organization, proposal ID, source/candidate revision, trigger kind (`business_signal`, `scheduled`, `manual_request`, `next_test`), policy version, status, attempt/lease, idempotency/request digest, context manifest ID/digest, qualified research request IDs, cost budget/actual bounded usage, start/end timestamps, safe outcome and failure code. Trigger kind records why a run began; it does not create a new Campaign source enum. Store sensitive source text in existing protected records, not worker payloads.
- Proposed worker `campaign.research-proposal`, composed in `src/workflows/campaigns/research-proposal.ts`, registered in `src/trigger/campaigns.ts`. Payload includes only organization/proposal/run/correlation IDs. PostgreSQL owns claim/lease/retry/completion; Trigger manages execution.
- Reuse qualified Growth research outputs through a source-owned public reader. Do not have Campaign call arbitrary web tools or bypass research provider/rights/budget qualification. A cited internal-only hypothesis can remain reviewable under D07 if external research is unavailable.
- Research performs bounded evidence/context selection, determines whether marketing can address the problem, drafts structured alternatives, validates factual/offer references, and persists a proposed version. It cannot approve itself or enqueue creative generation before proposal approval.
- Confirmed D06: automatic meaningful-evidence and scheduled research, plus manual requests. Each admission checks organization config, source fingerprint, cooldown, pending-proposal limit and research budget. A page load cannot enqueue it. Multiple triggers of the same evidence revision coalesce durably; a manual request cannot bypass limits or authorize creative generation.
- Proposed new `campaign_research_policies` stores organization, immutable policy version, enabled state, schedule/timezone, evidence qualification rule version and configured thresholds, cooldown, maximum pending proposals, per-run allowance and allowance per budget window with currency, creator and timestamps. Research allowance is distinct from media spend and creative preparation allowance. A controlled current-policy pointer and permission-checked update preserve audit history; no model edits policy. Missing settings produce Needs setup, with no default spending authority.
- Meaningful evidence is a source-owned revision passing configured qualification/freshness rules, not a repeated Memory projection or changed last-fetched timestamp. Persist evaluated source fingerprints and schedule due-window identities even when no research is warranted. Schedule and event races reuse one admitted request for the same candidate; do not exhaust budget by duplicating it.
- Persist cancellation and policy revision checks at admission and before further billable work. Pausing research stops new admissions and subsequent cancellable research work, retaining actual measured cost/history. It leaves live-campaign observation, provider reconciliation and stop handling operational.
- Reuse existing `campaign_generation_runs` for post-approval creative work. Add necessary proposal/context binding rather than building a competing generation queue. Bootstrap failures must be recorded even if the normal claim method never runs.
- Events are identifier-only past-tense domain events: proposed `campaign.proposal_requested`, `campaign.proposal_prepared`, `campaign.proposal_approved`, `campaign.proposal_changes_requested`, `campaign.creative_reviewed`, `campaign.launch_approved`, `campaign.investigation_completed`. Register schemas and durable capture/outbox intent in the same transaction; a logger-only publisher is insufficient.

## C04 — Finished deliverable and exact launch binding

- New domain file `src/domain/campaigns/deliverable.ts`; proposed `CampaignDeliverableVersion` and `CampaignLaunchManifest` types. Keep logical deliverable identity separate from immutable output versions and from provider action IDs.
- New tables proposed: `campaign_deliverables`, `campaign_deliverable_versions`, `campaign_deliverable_reviews`. Columns include organization/campaign identity and composite tenant links to exact bundle version, direction and optional creative variant, poster render or explicit existing final asset, template version, script, channel/placement, caption/hashtags/CTA, destination, content hash, verification record, created_at and current version pointer where mutable identity requires it.
- Reference finished bytes in private Storage through an existing owned asset/render link. No signed URL in a manifest, review or digest. Distinguish `finished_poster` from `final_image`; a textless plate is not automatically a final_image. Final asset eligibility is an explicit reviewed choice.
- Reviews bind exact deliverable version and content hash, actor and decision with reason/history. New versions do not inherit approval. File upload, successful OCR, Studio render success and human reference approval each have different meanings.
- Launch manifest binds exact bundle/proposal version, selected deliverable versions/hashes and all channel action terms, including caption, hashtags, CTA, destination, accounts, placement, script, timezone-resolved schedule, budget/expiry and pause policy. Include offer/claim source assertions and measurement prerequisites.
- Material changes invalidate affected future authority. Existing running objects retain their approved historical identity and history. Do not delete their approvals merely to hide version differences; use existing version supersession rules plus explicit action state.
- Reconcile bundle schema upgrade with existing version 2. Proposed new manifest version is 3 only after its schema/SQL validator/digest/backward reader design is approved. Never repeat historical “delete V1 data” instructions from the old preproduction release plan. Existing V2 records must stay readable, with explicit legacy launch eligibility.
- D05 is confirmed: every finished variation requires review. A generation policy/cap is not approval of new visible content. Variants may be prepared within approved cost caps but cannot dispatch until their finished versions are reviewed and included in launch approval. No unseen-variation publication mode is part of this redesign.
- Proposed endpoints: `GET /campaigns/:campaignId/deliverables`, `POST /campaigns/:campaignId/deliverables/:deliverableId/reviews`, `POST /campaigns/:campaignId/launch-approval`. Extend rather than ambiguously repurpose existing `/approve` behavior; legacy callers retain an explicit compatibility adapter or fail closed.
- Approval frontend may use one confirmation for creative review and launch terms. The database transaction still binds all required exact identities. Review selected outputs and schedule selected outputs cannot reference different sets.
- Dispatch resolves the selected deliverable version directly; never `direction.assetIds[0]`, newest render, current gallery selection or first account mapping. Provider-specific request types separate Instagram, Facebook and paid Ads. Include every approved public text field in the normalized request digest.

## C05 — Studio edit/render lifecycle

- Reuse `poster-template.ts`, `poster-studio-view.ts`, `poster-compositor.ts`, `plate-edit.ts`, `operator-edit.ts`, `patch-service.ts`, existing renders/edits/plate-edits routes and their claim/version checks.
- New UI read model `StudioEditSession` contains current immutable bundle/deliverable version, editable slot values, source-owned locked values, selected template/script/placement, preview status, reference summary, validation results and latest render identity. It is a view model, not a new authoritative mutable campaign document.
- Unsaved changes stay local. Persist a typed patch against base version/digest; server rechecks allowed fields and source assertions. An offer/price edit creates a proposal/business revision request if it changes approved intent; cosmetic wording remains subject to claim validation and new creative approval.
- Browser layout preview uses the same declarative template coordinates/slot mapping. Authoritative text shaping/render remains on the server with vendored fonts. Readiness requires exact render verification, not the browser preview's apparent fit.
- Stable render identity includes bundle/deliverable revision, plate hash, template version, script, exact slot values including free line, brand mark version and render engine/font version. Retry identical inputs reuses the recorded result; changes create a new render.
- Region edit binds parent plate hash/dimensions, validated normalized region coordinates and bounded instruction. Persist parent/child lineage; verify bytes outside allowed regions stay unchanged. Cancellation never overwrites the parent. A full regenerate is labelled as such.
- Supported scripts remain the existing Latin, Malayalam and Arabic set until more fonts and shaping tests are added deliberately. Unsupported script or missing glyph returns a named refusal; never silently switch font or transliterate.

## C06 — Creative History and uploads

- The approved correction is already defined in `2026-09-09-creative-history-asset-library-correction.md`; its selector/domain schemas and `20260909124757_creative_history_core.sql` exist. Reuse `creative_folders`, `creative_items`, `creative_item_versions`, `creative_item_reviews` and `creative_item_performance_evidence`; do not add duplicates under different names.
- Complete its missing service/repository/API/UI and pinned-run receipt tasks. Read existing strict schemas/SQL before adding fields. Preserve immutable versions, review history, rights and confirmed versus proposed metadata.
- Upload transaction sequence: reserve tenant/path/version intent → transfer bytes into private storage → server sniffs/validates/re-encodes/strips metadata/hashes → finalize immutable usable version → optional descriptive metadata proposal → human confirmation/review.
- File constraints come from the active `asset-intake` contract and Storage configuration, not copied browser constants. Expose permitted types/size in the upload DTO. Client validation gives early feedback; server validation remains authority.
- Each client upload has a unique local ID plus stable persisted intent ID; duplicate filenames cannot collide. Retrying after a lost finalize response uses the same intent/digest and returns the same version. Same key with changed bytes is a conflict.
- Reserve/sign/finalize routes enforce organization, manage permission and version ownership. A failed finalize response, including a 200 typed refusal, cannot show Uploaded/Ready. Distinguish bytes transferred, processing, usable, needs review and refused.
- Partial batch success leaves good items available; retry only failed items. Cancellation and abandoned intents have bounded cleanup based on authoritative reservation status. Never delete arbitrary Storage objects from browser input or roll back completed uploads in a failed batch.
- Selection pins at most 3 approved designs, 5 rejected designs for Blueprint only and 12 supported negative rules, per ADR 0049. Weak/unreviewed/unconfirmed/archived/ineligible-rights candidates are omitted with reasons. Relevant product/occasion/channel/format/market/language/objective dominate generic similarity; performance is secondary comparable evidence.
- Final-image API accepts `FinalImageReference[]` only; Blueprint API accepts `BlueprintEvidenceReference[]`. Separate runtime construction/validation, not a cast or shared array filtered only by prompt text. Final calls cannot access rejected IDs/paths for later loading.
- A completed Studio render can be linked once into history as Unreviewed through a controlled idempotent completion path. Re-reviewing reference eligibility never mutates past generation receipts.

## C07 — Provider execution and confirmed pause

- Reuse Tool Gateway, credential store, campaign action runs, budget reservations, receipts, exposure and pause/reconciliation domain adapters. Register actual qualified adapters at the composition root; do not create a second gateway for the redesigned UI.
- Contract freshness, provider credentials, account eligibility, granted scopes, mapping, adapter version, object reconciliation and launch content limits are independent proof requirements. Missing any one blocks only affected actions with a safe reason.
- Separate paid campaign/ad-set/ad object graph from organic content posting; bind all created external IDs before subsequent writes. Retry must not duplicate intermediate objects. Verify provider pause and unknown-outcome reconciliation before enabling live paid spend.
- Proposed versioned organization/campaign pause policy stores permitted deterministic rule IDs/versions, exposure floor, applicable metric reporting delay, window and numeric thresholds/ceilings, currency, approver and effective period. Numeric thresholds must be explicitly configured and approved. Existing global environment values are not a durable per-tenant policy.
- Pause states: requested, submitting, confirmation_pending, confirmed_paused, refused/failed. These are proposed action-state semantics, not direct replacements for existing variant enums. Variant becomes paused only when the provider's effective delivery state confirms the stop.
- Read-back disagreement or timeout leaves confirmation pending and alerts the operator. Provider/account revocation, missing object ID, and ongoing spend have explicit escalation paths. Reconciliation is idempotent and never treats lack of metrics as proof of a pause.
- Human resume requires current authority and limits, a governed resume invocation and confirmation. Local state changes alone never imply delivery resumed.
- Cadence sweeps are gated by organization config and policy; do not activate all tenants from a deploy-wide cron. Record missed/failed cycles and stale metrics. Ensure paused/ended ads can still receive delayed conversion observations.

## C08 — Clinical investigation and the next cycle

- New files: `src/domain/campaigns/investigation.ts`, `application/investigation-service.ts`, `infrastructure/investigation-repository.ts`, `infrastructure/investigation-drafter.ts`, `src/workflows/campaigns/investigate-performance.ts` and focused tests.
- New tables proposed: `campaign_investigation_runs` for bounded durable work; `campaign_investigations` for immutable structured reports keyed by organization/campaign/evidence digest. Add a source-owned exact-version link to the proposal generated for a next test.
- Investigation input includes exact deliverable/variant identities and human review, creative features with model/source attribution, audience/placement/objective, actual delivery periods, observed spend and metrics, attribution/reporting windows, pause events, baseline/result limitations, and approved comparable historical evidence.
- Comparison first returns deterministic comparability status and exclusion reasons: different objective, unmatched audience/placement, unequal maturity, insufficient exposure, missing conversion data, currency conflict or noncomparable attribution. AI cannot override this with a confidence score.
- Report structure: `observations`, `comparisons`, `hypotheses`, `counterEvidence`, `unknowns`, `suggestedNextTest`, `evidenceRefs`, `contextRefs`, model/usage/version metadata. Each hypothesis identifies the outcome it might explain and its support/limitations. All referenced records must be in the pinned permitted evidence set.
- Hypotheses may discuss offer, audience, visual treatment, message, placement, timing, frequency/delivery saturation or landing experience only where matching evidence exists. Do not infer unavailable conversion paths or competitor economics.
- A suggested next test describes one meaningful proposed change, retained controls and desired evidence. AI may propose that change; deterministic registered methods, approved thresholds and human budget/launch approval remain authoritative.
- Keep existing settlement verdicts and proof unchanged. Early diagnostic investigation may say what to inspect; it cannot prematurely settle a causal outcome. A paused ad can be investigated while late observations remain pending.
- Capture factual source outcomes and investigation observations through Spec 023's durable capture contract with their proper trust level. A proposed reusable lesson enters the existing governed Memory review path. No automatic permanent avoid rule, verified fact or playbook update.
- Metrics DTOs distinguish missing, stale, observed and settled; include units, currency, numerator/denominator, window, source revision and attribution method. Aggregate rates from compatible counts, never average percentages. Do not sum overlapping audience reach or mixed-currency spend.

## C09 — Read models, tenancy, diagnostics and compatibility

- Campaigns owns portfolio, detail, deliverable, preview, performance and proposal read services. Growth Intelligence and Organizations compose safe public DTOs; they do not reproduce Campaign table logic or depend on Campaign UI internals.
- Read APIs use session clients/RLS and current permission checks. Private previews use session-authorized source identity and bounded URL expiry. Keep a safe no-preview state on failed signing. No service role on a user-facing path.
- New tenant tables have RLS and composite organization foreign keys, appropriate SELECT/mutation grants, immutable-history guards and bounded indexes. Mutations use scoped controlled RPCs; privileged worker RPCs revoke PUBLIC/anon/authenticated and validate organization/run/lease. Check actual capability mappings rather than broad “not viewer” conditions.
- Audit sensitive changes with organization, actor, source identity/version, decision kind, correlation and event timestamp. Worker telemetry records task/run, stage, elapsed time, actual bounded cost/usage and safe reason. Prompts, raw provider responses, customer information, Storage credentials and signed URLs never enter public errors/logs.
- No plan task may claim zero model cost because an attempt failed. Unknown stays unknown until measured usage is available; failed bounded calls preserve what was measured.
- Backward readers preserve existing campaigns, V2 manifests, renders, approvals, reference receipts and outcomes. New paths feature-gate by organization; rollback stops new admissions/execution while leaving history readable. Disabling a feature does not stop ads already running at a provider; their containment path must remain operational.
- Introduce schema changes through forward migrations, narrow hand-maintained `database.types.ts`, hosted dry-run/application approval and executed staging RPC tests. Never start local Supabase/Docker, run `pnpm db:types`, stash, broadly format or git push.
