## 4. Production data contracts and invariants

- [ ] Monetary inputs are integer minor units plus currency. Use existing `formatMoney`, `formatWholeMoney`, `formatCount` and currency exponent resolution. Do not divide by 100 universally; JPY/BHD tests are required.
- [ ] Build active rows with `row.status === 'active'`. Every active registered channel must have one row in the ready view; use the existing refused representation for a missing analysis row rather than inventing a figure.
- [ ] Reported total sums nonnull `band.potential` from active complete and revenue-only rows only if all contributing currencies are usable and equal. No records => null; genuine zero records => zero. Guard integer addition against an unsafe sum; refuse aggregate on overflow, never silently round.
- [ ] Earned/lost totals sum the corresponding already-derived fields from active complete rows only, with usable equal currencies. Do not calculate per-channel earned again; the shared `describeChannelMoney` already owns that relationship. No complete rows => both null.
- [ ] Mixed-currency revenue-only rows can block the reported total/chart while a currency-consistent complete subset still has an earned/lost total. State the contributing count and currency for each metric; never sum or share across currencies.
- [ ] `reportedCount` counts nonnull potential including recorded zero; `completeCount` is state complete; revenue-only and refused counts remain separate. Percentage denominator is `reportedTotal.minorUnits`, not complete-band potential, earned total or number of channels.
- [ ] A zero denominator means share unavailable, not 0% for everyone. Negative reported amounts stay signed in the directory/exact-value detail; use an explicit “Share comparison is unavailable for signed adjustments” state for the proportional chart. Do not use absolute values or clamp negatives into positive bars.
- [ ] A `refused` band may mean no source, incompatible loss or invalid relationship. Label it `Needs review`, description `No comparable revenue figure for this window.` The coverage rail's third label is `No comparable figure`; do not invent which report failed from this narrow model.
- [ ] `Measured` means both monetary inputs are available, not complete daily coverage, verified profit or successful recommendations. The model does not carry freshness or full lineage metadata. Do not fabricate last-fetched timestamps, run freshness dots, source IDs, quality percentages or “all locations verified”.
- [ ] The green reporting-window dot marks context, not live status. Its adjacent text must say `reported window`; tooltip/dialog explains selected dates. Hide it or use neutral styling when no valid selection exists.
- [ ] `view.selectedWindow === null` with declared options means the requested selection was not recognized: suppress figures and show `Choose a reporting window.` Do not put unknown dates above fallback values. The page's existing default resolver runs only when URL parsing returns null.
- [ ] Current window read is capped at 24 declared windows; this plan neither expands the bound nor invents a full historical calendar. Keep all returned options, including multiple ranges in one month and span grains.
- [ ] Keep source time boundaries as date-only strings. Format through UTC-safe date-only construction with explicit UTC for labels so browser timezone cannot move the date. Never relabel Jan 1–Feb 28 as February alone.
- [ ] The scope caption is `Reported scope · {currency}` when one comparison currency exists, `Reported scope · Multiple currencies` on a mismatch, or `Reported scope` with no money. No branch selector or currency-conversion selector is added.
- [ ] Archived directory records show original channel identity/history links. If the returned view has a monetary band for them, label it `Historical reporting window`; never divide archived revenue by the active portfolio total. No fresh archived analysis request is triggered.
- [ ] Location labels describe configuration, not measured evidence coverage: no mappings => `Organization-wide`; mappings => distinct configured active mapping count with noun `mapped location(s)`, plus `{n} historical` for inactive mappings. If no active mappings remain, say `No active mappings`, retain history, and do not silently turn history into all-location applicability. Effective dates remain visible in Manage; this count does not assert the map was effective for the analysis period.
- [ ] Alias rows in the snapshot are active aliases only. Do not present that as all-time alias history. Preserve original alias text, normalized matching rules, source scope and dates. An alias is one exact label; do not split punctuation or semicolons automatically.

## 5. Mutations, permissions and error behavior

- [ ] Keep the existing same-origin endpoints and authenticated cookies. No direct browser Supabase writes or service-role reads. No auto-retry of writes: explicitly set mutation `retry:false`, especially for alias creation.
- [ ] **Create:** POST `/api/organizations/{organizationId}/channels`; body `{key,displayName,category,templateKey}`; success 201 `{channel}`. Initial create saves identity only, then presents the created channel's Manage dialog so mappings/labels can be added separately. Show `Channel created.`; do not report setup complete.
- [ ] **Identity update:** PATCH `/api/organizations/{organizationId}/channels/{channelId}`; body `{displayName,category,templateKey}`; success `{channel}`. Never submit `key` on edit.
- [ ] **Archive/restore:** PATCH same URL, body `{status:'archived'}` or `{status:'active'}`. Require the local confirmation dialog; do not DELETE. Preserve history and prevent repeated submissions while pending.
- [ ] **Location mapping:** PUT `/api/organizations/{organizationId}/channels/{channelId}/branches`; body `{branchId,applicability,effectiveFrom,effectiveTo}`; success `{mapping}`. One mapping per request; switching from active to inactive preserves it. No bulk “All locations” pseudo-ID or clear-all action.
- [ ] **Report label:** POST `/api/organizations/{organizationId}/channels/{channelId}/aliases`; body `{alias,sourceScope,effectiveFrom,effectiveTo}`; success 201 `{alias}`. Existing aliases are read-only entries; no edit/delete endpoint exists in this route set.
- [ ] Zod input rules: stable key trimmed/lowercased matching `^[a-z][a-z0-9.-]{1,80}$`; display name trimmed length 1–160; provider hint null/omitted or same key schema; categories exactly marketplace/owned_digital/physical/reseller/other; alias length 1–300; branch ID UUID; optional dates strict dates and end not before start. Do not copy prototype's 60-character name limit or 180-character alias limit.
- [ ] Do not silently invent a stable key from a name. Show Stable key as an editable required creation field and read-only field on edit; optional provider hint remains under Advanced identity settings. Exact copy in visual contract.
- [ ] New response validation belongs in `channel-mutations.ts`: validate envelope/resource identity (`id` UUID, expected `organization_id`, `channel_id` for mappings/aliases, expected status for status writes) and pass through unused fields. A 2xx missing the expected object or returning another tenant/channel is not a successful save. Treat malformed/non-JSON response as a safe error.
- [ ] A TanStack `useMutation` hook per operation is sufficient. Use mutation keys beginning `['channels',organizationId,channelId-or-'new',operation]`. Inputs contain drafts, not server records; server state stays in RSC props. `onSaved` uses router refresh; there is no new GET/query cache to invalidate.
- [ ] `canManage` controls create, identity edit and archive/restore. `canMapBranches` independently controls location and label writes. Operator with mapping permission can open Manage but sees identity/status read-only. Viewer gets `View details` in the same ellipsis position and all configuration read-only; no enabled mutation controls.
- [ ] Channel Audit/Open channel/View history links remain available to readers regardless of manage permission. Hide audit-specific wording when analysis gate is off; retain navigation to existing setup-capable detail.
- [ ] Mutation pending: retain input values, disable related submit and conflicting actions, display installed Spinner followed by Saving…/Creating…/Archiving…/Restoring…. Do not close the dialog or show success before validated success. Avoid a second write while one section is pending.
- [ ] On rejected fetch, non-2xx, malformed response or envelope mismatch: reset pending, retain draft values and modal, render section-specific Alert, focus or announce its title, offer Retry through the same submit. Do not expose raw request payloads, provider errors or stack traces. Public error message may be used only from the established `{error:{code,message}}` envelope; fallback strings below remain mandatory.
- [ ] Identity error: `Channel was not saved` / `The channel could not be saved. Please try again.` Mapping error: `Location mapping was not saved` / `The location mapping could not be saved. Please try again.` Label error: `Report label was not saved` / `The report label could not be saved. Please try again.` Archive error: `Channel status was not changed` / `The channel status could not be changed. Please try again.`
- [ ] Success messages: `Channel created.`, `Channel saved.`, `Location mapping saved.`, `Report label saved.`, `Channel archived.`, `Channel restored.` Use the existing root Sonner. Never mount another Toaster or copy the prototype's fixed green toast div.
- [ ] Partial success across sections is explicit: successful identity save remains saved if label save fails. Each section has its own Save and status. Do not roll back unrelated successful operations client-side or claim an atomic multi-section transaction.
- [ ] After create, use the validated returned ID to transition to Manage; refresh the server snapshot. Preserve the newly created record locally only as the mutation result until refreshed props contain it; do not substitute fictional money or branch data.
- [ ] Handle stale props on refresh: keep unsaved drafts for their section; reset a section after its successful response; choosing another channel remounts drafts keyed by ID. When the selected channel disappears from the refreshed allowed snapshot, close it and clear local selection.
