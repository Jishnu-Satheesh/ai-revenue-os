# Independent Creative Studio: provider and Asset Library audit

Date: 2026-09-20. Design-only evidence; no provider generation, database inspection, production code, or existing governance changes. Public provider documentation fetched through TinyFish; private repository material was not submitted. Current provider account/model availability remains untested.

## Decision

The user confirmed that AI generates the **entire poster, including the supplied Text Copy verbatim**, followed by spelling/layout review before approval. The new standalone Studio design must explicitly supersede Spec 020’s no-model-text rule for this new workflow only; the existing Campaign exact-text compositor retains its contract. A standalone, brand-guided full-poster workflow is plausible. It needs a new conversation-aware provider contract; the current Campaign image adapter is insufficient. Keep the requested **Exact design** and **Take Inspiration** choices, but describe Exact design as preserving the selected layout, style and content placement while making requested changes. Neither a prompt nor a model API guarantees identical pixels, exact lettering, or an undistorted mark.

**Updated user requirement: visible progressive image previews are mandatory.** Progress text followed by only a final image is not an acceptable fallback. Qualify another provider if Gemini cannot prove independently displayable intermediate previews. A simulated reveal is not provider streaming. Release is blocked until an actual provider test proves preview frames and durable same-image-model multi-turn editing together.

## Public provider findings

Sources were retrieved on September 20, 2026; provider docs are mutable.

- Google’s [image-generation guide](https://ai.google.dev/gemini-api/docs/image-generation) documents full image editing, supplied-logo composition, and image conversations. Its current examples use the Interactions API and `previous_interaction_id`. The guide distinguishes Gemini 3.1 Flash Image from Lite; Lite is not optimized for multi-reference sequential editing. A model choice requires a live qualification rather than assuming every image model behaves alike.
- The same [image-generation guide](https://ai.google.dev/gemini-api/docs/image-generation#limitations) documents model-dependent reference limits (up to 14 in the Gemini 3 family), variable fidelity by object/person count, and supported ratio/size tables. Keep the existing three-approved-history-reference ceiling unless explicitly changed; product/brand/parent/marker images also consume request capacity. Standard 1:1, 4:5 and 9:16 have documented support. Requested pixels are not guaranteed pixels; validate actual dimensions and define any final resize/crop visibly.
- The [Interactions guide](https://ai.google.dev/gemini-api/docs/interactions) describes server-side continuation and stored interactions. Prior-interaction chaining preserves conversation inputs/outputs, while other configuration is interaction-scoped. Store/retention/deletion must be deliberate: `store=false` prevents later continuation by that ID. This is an integration/privacy choice, not a cache toggle.
- [Streaming interactions](https://ai.google.dev/gemini-api/docs/interactions/streaming) documents SSE step events and base64 `image` deltas as well as text deltas. An image delta is documented image data, not an explicit guarantee of multiple independently displayable previews of the same image. Qualification must establish decoding/assembly and event timing for the selected image model.
- [File input methods](https://ai.google.dev/gemini-api/docs/file-input-methods) currently documents a 100 MB request/payload ceiling for inline and external-URL inputs. Do not reuse the older 20 MB figure or equate a total encoded request ceiling with raw per-file bytes. This page also lists method-specific MIME differences; use the intersection of the chosen method, model and application intake.
- [Context caching](https://ai.google.dev/gemini-api/docs/caching) describes implicit cache hits as cost/performance behavior in stateful and stateless modes. A cache hit is not conversation identity, persistence, or a continuity guarantee. Do not sell cached editing or promise savings.
- [Image understanding](https://ai.google.dev/gemini-api/docs/image-understanding#supported-image-formats) lists PNG, JPEG, WebP, HEIC and HEIF. Current application image intake is narrower (PNG/JPEG/WebP). Preserve that boundary unless an approved intake change adds conversion. SVG brand/channel artwork needs validated rasterization before model submission; never assume SVG acceptance.
- [Files API](https://ai.google.dev/gemini-api/docs/files) documents a 2 GB per-file and 20 GB project storage ceiling with 48-hour file lifetime. Those are storage limits, not this product’s upload allowance or a promise that a given image generation request accepts that payload. Provider file IDs cannot replace durable private application objects.
- The live [thought-signatures page](https://ai.google.dev/gemini-api/docs/thought-signatures) returned only a heading and footer in this retrieval. Do not invent a current signature requirement from it. Local adapter code proves support for opaque signatures; the chosen model/API needs an actual continuation test and appropriate current API reference before implementation.

A complete poster can include text and provided organization/channel logos. Store supplied Text Copy as the exact user-authored source; do not let a planning model paraphrase it. Prompt the image model to reproduce it verbatim. Record brand fonts as guidance: a raster model output does not prove the requested font file was used, and neither supplied font names nor a typography reference guarantee exact typeface fidelity. Run OCR against the stored copy as a review aid, show suspected missing/changed text and low-confidence regions, and require human full-size spelling/layout review before approval. OCR is fallible, especially for stylized or non-Latin text, and must not be described as proof of exact text. Font/logo/text failures are visible revision reasons, not reasons to secretly replace the full-poster workflow. No reviewed primary source promises typo-free exact text or pixel-exact trademark reproduction. Supply approved channel-logo bytes, never ask the model to invent an official mark; review full-size output before export. Do not silently switch this independent workflow to the existing deterministic compositor if full-poster generation is the approved product choice. If faithful marks/text cannot pass the feasibility examples, return that concrete quality failure for a design decision.

## Proposed contract, not implemented

- Workspace belongs to one organization and is independently addressable. A session pins provider, exact model ID, API family, capability profile and brand snapshot. A model change starts an explicit new context branch.
- Each user turn pins parent output revision/hash, ordered typed reference versions (approved design / product / brand or channel mark), selected mode, exact requested copy, target ratio and marker coordinates normalized to the unscaled parent image.
- Dispatch reauthorizes membership and revalidates every reference/version/review in that organization. Upload success means finalized valid bytes; design approval remains a separate human decision. Uploaded finished references need that review before appearing under Approved designs.
- Context binding records ordered user/assistant turns and output revision ancestry. For GenerateContent, retain provider parts and opaque thought signatures; for Interactions, retain interaction lineage plus required per-turn configuration and a documented retention/recovery policy. Do not mix both protocols or interpret signatures as chain-of-thought for display.
- Parent image is the clean canonical output. Marker overlay is a separate input with indexed instructions; normalize orientation and scaling. Markers indicate intent, not a hard editing mask. The whole regenerated poster needs review, and earlier revisions remain selectable.
- Events are persisted and reconnectable: accepted, preparing references, generating, receiving image, validating, ready, failed/cancelled. Optional text deltas are user-facing status only; never raw thought output. `ready` requires complete validated stored bytes. Required preview-frame events must contain complete independently decodable intermediate images and be supported by qualified provider evidence. Progress events supplement these frames and cannot replace them.
- Outputs store actual MIME, dimensions, bytes/hash, model/API/version, turn and parent IDs, reference manifest, policy/result status and safe failure code. Refusal/no-image differs from timeout; unknown provider completion is not an invitation to blind automatic retry.

## Provider feasibility gate before implementation commitment

Use an explicitly authorized, bounded provider test later; none was run for this audit.

1. Pin an available model/API; prove installed SDK compatibility or propose an explicit adapter/dependency change. Use the same pinned model for first generation and all edits.
2. Generate complete posters in 1:1, 4:5 and 9:16 using approved design, product and logo references. Inspect actual dimensions, exact copy, logo quality, product fidelity and adherence to hard brand rules.
3. Record event timestamps and types without private payloads. Demonstrate whether the stream contains text, complete images, or independently displayable intermediate image frames. Make the UX claim match that evidence.
4. Persist a first turn, reload in a new process, edit with a marker, then perform a second contextual edit. Verify ordered parts/signatures or interaction lineage survive, and revising an older output branches from that output rather than the latest unseen turn.
5. Test no-image response, invalid image bytes, expired provider file/context, request cancellation/disconnect, concurrent edits, model unavailability and oversized multi-reference requests. Show safe recovery without silent context loss or duplicated paid work.
6. Verify cross-organization IDs and revoked/changed reference approvals are refused before private bytes leave the application. Check output remains unreviewed until human review.

If the chosen provider cannot emit progressive images, reject that provider for this workflow and qualify another. Do not ship progress-only streaming. The user explicitly requires visible progressive previews; actual frame decoding/display and same-model contextual multi-edit proof are hard release gates.

## Required progressive previews: prospective provider qualification

Updated September 21, 2026 to reflect the explicit user decision; primary documents below were fetched September 20. **OpenAI Responses API with its image-generation tool is the first prospective provider to qualify**, because its official guide documents both preview-image events and contextual editing. This is a design recommendation, not a claim of verified account access or completed integration.

- [OpenAI image generation — streaming](https://platform.openai.com/docs/guides/image-generation#streaming) documents `partial_images` from 0–3 and `response.image_generation_call.partial_image` events. Its examples independently decode `partial_image_b64` and save each preview as a PNG. This is stronger evidence for displayable intermediate frames than Gemini’s generic image-data deltas. Requested preview count is not guaranteed when generation finishes quickly; never invent frames or count the final image as proof of progressive output.
- [Multi-turn image generation](https://platform.openai.com/docs/guides/image-generation#multi-turn-image-generation) documents continuation through `previous_response_id` or image-generation outputs/IDs supplied as context, plus `action: "edit"` when an image is already in context. Pin both the orchestration model and the image tool’s exact model; “same model” means the image model actually rendering the pixels remains constant. Store response ancestry alongside application revision ancestry, enforce tenant ownership before replay, and test continuation after a new process/browser reload.
- The current [image-generation guide](https://platform.openai.com/docs/guides/image-generation) names `gpt-image-2.5-sunburst` and `gpt-image-2.5-flare`, recommending Sunburst when editing precision matters. These mutable names require live account qualification; do not substitute a remembered older model. The repo has no direct `openai` or `@ai-sdk/openai` dependency or top-level installed package in this audit. A new adapter/dependency and credentials are explicit future implementation scope.
- The current guide supports custom dimensions subject to multiples of 16, ratio between 1:3 and 3:1, maximum edge 3840 and total pixels 655,360–8,294,400. Standard recommendations include 1024×1024, 1536×1024 and 1024×1536. PNG/JPEG/WebP output is documented. Exact export pixels still need deterministic final sizing and actual byte validation.
- Fidelity is model-specific: the guide’s earlier-model section says `gpt-image-2` always processes inputs at high fidelity and rejects changing `input_fidelity`. Do not copy `input_fidelity: "high"` into every future model request. Qualify the exact chosen model’s schema and product/logo/text preservation. The guide explicitly acknowledges remaining text-placement, visual-consistency and precise-composition limitations.
- [OpenAI conversation state](https://platform.openai.com/docs/guides/conversation-state), fetched September 21, documents response objects retained for 30 days by default and `store: false` as an opt-out. Response-ID chaining is not permanent application storage, nor a cost-free cache; prior chain input tokens remain billable. Define deletion/expiry recovery using application-owned canonical images and ordered conversation state, and never silently start a fresh context after an unresolved response ID. Retention and tenant-bound response IDs are part of adapter qualification.
- OpenAI input MIME/count/size limits remain a model-and-endpoint qualification check: the retrieved Images API page did not expose a reliable complete edit-input schema. Keep the application’s existing validated PNG/JPEG/WebP intake and effective byte limits, and verify the selected Responses image-input path accepts them. Do not mistake documented PNG/JPEG/WebP **output** choices or the mask ceiling for a verified general input limit.
- Mask editing is optional and distinct from marker annotations; the guide requires matching mask/image format and dimensions, under 50 MB, with mask alpha. Do not treat an ordinary numbered marker overlay as a provider mask or guarantee unchanged pixels outside it.

**Hard qualification test:** request partial previews and capture at least one real, independently decoded, visibly displayed pre-final image on generation and on contextual edit; then reload, edit again using the same pinned image model, and prove exact parent/context lineage. Preserve event IDs/order, received times, image hashes/dimensions and screenshots without raw prompts or private image bytes in logs. Exercise reconnect, cancellation and failed/no-preview outcomes. A fast response producing only a final image cannot count as the progressive-preview acceptance proof. If no provider can meet this, record a blocked capability; do not downgrade the requirement.

Meta’s cited pages specify JPG/PNG and a 30 MB maximum; Google’s cited Performance Max page specifies JPG/PNG and 5 MB. Effective export encoding limits and placement rules must be checked at export; the library upload allowance is a separate boundary. Google recommends at least one image without overlays for each ratio, while its responsive display assembly separately combines images, headlines and logos. A full-poster draft with baked text is therefore not sufficient to claim a complete Google campaign asset set.

**Amazon is placement-specific.** The official [Sponsored Brands Product Collection custom-image specification](https://advertising.amazon.com/API/docs/en-us/guides/sponsored-brands/ads/product-collection) lists at least 1200×628, PNG/JPG, up to 5 MB, and forbids added text, graphics or logos in the custom image. That same current page marks Product Collection deprecated with shutdown in January 2027 and directs new work toward Collections. It is evidence that a generic full-poster-with-copy preset cannot be advertised as universally Amazon-compatible; it is not a recommendation to implement a deprecated placement. A future Amazon preset needs a named current placement and fresh specification audit.

**Fit/pad/crop contract:** choose the final export size before generation and show its frame plus safe area. Prefer a supported native ratio matching it, then proportional resizing after checking actual dimensions. For a ratio mismatch default to containing the entire poster with visible, brand-compatible padding; preview that padding before export. Cropping requires an explicit crop preview/choice and rechecking all text, logo and product bounds. Never stretch a poster, silently clip copy, or claim a dimension prompt ensures native compliance. Gemini’s documented 4:5/9:16 raster dimensions can themselves be approximate ratios, so measure bytes rather than assuming an exact ratio from the configuration label. Every resized/cropped/padded export is a versioned derivative linked to the accepted parent.
